## A. Normal step

You are continuing the BRICS ERP project. **Step for this session: `P_._`**

**1. Load context (read the brain, not the codebase)**
Read `AGENTS.md` → `.brain/00_INDEX.md` → `.brain/PROGRESS.md` (especially "Resume here") → the `.brain/FEATURES.md` rows for this step's feature IDs → only the relevant `.brain/modules/*.md`. Open source files only when the step needs them.

**2. Preflight: start from green**

- Check `git status` is clean and you are on the last green commit from "Resume here".
- Run the green gate for the apps this step touches. **P track (P0–P13, backend + web): JS gate only — `pnpm lint && pnpm typecheck && pnpm test && pnpm build` plus backend e2e. Flutter is not installed; never run `flutter analyze` / `flutter test` and never report `mobile/` as red.** M track (M0–M6, only on a machine with the Flutter SDK): also `dart run build_runner build -d && flutter analyze && flutter test`.
- If anything is red **before** you start, fix that first, commit it as `fix: …`, and tell me. Do not build new features on a red base.
- If a required tool is missing on this machine, tell me how to install it before you continue.

**3. Scope check: Client Phase and depth**

- State which Client Phase this step belongs to (**CP1 MVP** or **CP2 Advanced**) and list the feature IDs it covers.
- **CP1 rule:** build exactly the depth written in FEATURES.md. Anything more advanced goes in FEATURES.md → "CP2 candidates", not into code. Correctness (balanced journals, stock formula, GST split, tenancy, audit) is never cut.
- If the step looks too big for one session, propose a split (e.g. `P5.1a` / `P5.1b`) now.

**4. Plan, then wait for my OK**
Give a short plan:

- **Backend:** entities, migration(s), endpoints, posting rules (Dr/Cr), stock effects.
- **Web:** pages, components (reuse existing ones first; create shared components, never duplicate).
- **Mobile:** screens, Drift tables, sync behaviour (**M track only** — P-track steps have no mobile part; what they owe mobile is `SYN-01` idempotency on create endpoints).
- **Tests:** what is covered (mandatory for accounting, stock and GST logic).
- **Questions:** anything ambiguous. Add them to `.brain/OPEN_QUESTIONS.md` too.

Wait for my OK. (If I wrote "go" with the step ID, go straight ahead after showing the plan.)

**5. Build in small, green, committed slices**

- Follow `.brain/CONVENTIONS.md`. Parallel sub-agents per app are allowed; you own consistency.
- After each slice (e.g. entity + migration, then service + tests, then controller, then UI), run the gate and **commit** (Conventional Commits).
- Migrations are append-only. No `synchronize: true`. Dev servers run in the background only, and you stop them when done.

**6. Final green gate**
Everything this step touched must pass: lint, typecheck, tests, build (+ `flutter analyze`/`flutter test` **only on the M track, where Flutter is installed**). Start the backend once and check `/api/v1/health`. If something cannot be made green, revert or disable the unfinished part, keep the last green state, and record it as ⚠️ with the reason.

**7. Update tracking (never skip; this is how we know what's done and what's left)**

- `.brain/FEATURES.md`: set each feature's per-app columns **BE · Web · Mob · Tests** and its overall **Status** (⬜ 🟨 🧩 ✅ ⚠️ ⏭️ —). Use 🧩 when a part is built but not connected (e.g. API done but the web/mobile screen is not using it yet). ✅ only if built + connected + tested + documented.
- `.brain/API_INDEX.md`: one row per endpoint touched, with **BE · Web · Mob** wiring status. Add rows for planned endpoints too (BE ⬜).
- Run **`pnpm status`**. It validates the symbols and regenerates the summaries, per-app progress, wiring gaps and `docs/13-roadmap-and-status.md`. Fix any error it prints.
- `.brain/PROGRESS.md`: mark the step, update % of CP1 done, and fill **"Resume here"** (last green commit hash, done, half-done, exact next step, blockers).
- `.brain/CHANGELOG.md`: a dated entry with feature IDs.
- `.brain/modules/*.md`, `DB_SCHEMA.md`, `ACCOUNTING_RULES.md`, `DECISIONS.md` (if a choice was made).
- The touched `docs/modules/*.md` (`docs/13-roadmap-and-status.md` is generated by `pnpm status`; don't edit it by hand).
- Commit: `docs(brain): update tracking after P_._`.

**8. Report**
What's done (feature IDs, per app), the wiring gaps from `pnpm status` (APIs not used yet, screens waiting for APIs), how to test it (commands + clicks), what's remaining in this phase, what's next, blockers, open questions. **Do not start the next step.**

## D. SaaS platform step (the S track)

You are continuing the BRICS ERP project. **Step for this session: `S_._`.** This is the **S track** — the vendor's own surface for selling BRICS to many kilns. It is not part of CP1, and a kiln's own experience must not change.

1. **Load context.** `AGENTS.md` → `.brain/PROGRESS.md` → **"Resume here: S track"** → `.brain/modules/saas-platform.md` → **ADR-052** in DECISIONS.md → the **PLT-** rows in FEATURES.md. Open source files only when the step needs them.

2. **Preflight.** Same as §A.2 — clean tree, green gate first. The S track runs on the P-track stack (NestJS + Next.js), so the JS gate applies in full: `pnpm lint && pnpm typecheck && pnpm test && pnpm build` plus backend e2e. Flutter is not involved.

3. **Hold these four, they are decided (ADR-052) — do not quietly redesign them.**
   - A platform admin holds **no business permissions**. Business access comes only from an active support session, scoped to one tenant.
   - The tenant list shows **metadata only** — counts and dates. Never an amount, never the client's own parties. The test for a new field: would the kiln mind a competitor seeing it?
   - Support access is **announced afterwards and expires** — a reason typed in, two hours, closed automatically, every audit row marked. Not approved beforehand.
   - `/admin` is **its own surface**, with its own navigation and no business menu.

4. **Plan, then wait for my OK** — as §A.4, plus: say which existing behaviour the step changes for a _kiln_ user. The answer should usually be "none"; when it is not, say so plainly before building.

5. **Build, gate, and update the brain** — follow §A.5 to §A.8 unchanged. The CP1 e2e suite is part of the gate for every S step: the S track touches guards, permissions and the audit log, which is exactly the machinery CP1 runs on. A green S step that reddens CP1 is a failed step.

6. **One thing that has bitten before.** Creating a company seeds the chart of accounts but **not** a financial year. Anything that onboards a tenant must create its first FY too, or the go-live import stops on its first row.
